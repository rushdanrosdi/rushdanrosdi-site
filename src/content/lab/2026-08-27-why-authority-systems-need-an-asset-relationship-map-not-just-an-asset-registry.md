An asset registry tells us what exists.

An asset lifecycle tells us what happens to each asset over time.

But there is still another question:

> How do the assets relate to one another?

A framework may be supported by several Lab Notes. A case study may support a service page. A LinkedIn post may distribute a Lab Note. A buyer question may be answered by several different assets.

Those relationships matter.

That is why I think an authority system eventually needs an asset relationship map.

## An asset registry describes the node

The registry can tell us what an asset is, what role it plays, which buyer stage it supports and whether it is current.

Useful.

But the missing layer is:

```text
Supports
References
Extends
Distributes
Reuses
Replaces
Depends on
```

Now the asset is part of a network.

## Authority compounds through relationships

A strong authority system is rarely one page.

It is usually a set of connected assets that reinforce one another.

For example:

```text
Buyer Question
→ Service Page
→ Case Study
→ Lab Note
→ Framework
→ LinkedIn Distribution
→ Conversation
→ New Buyer Question
```

Each asset does a different job.

The value comes partly from the relationships between them.

## Relationship mapping reveals isolated assets

Some assets may be strong but disconnected.

For example:

```text
Case Study A
Strong proof
No links from service pages
Not referenced in proposals
Not reused in distribution
Not connected to buyer questions
```

That is a useful asset with weak system integration.

The problem is not content quality.

The problem is connection.

## Relationship mapping can reveal over-dependence

The opposite problem can also happen.

Too many claims may depend on one weak asset.

For example:

```text
Service Page A
Framework Page B
LinkedIn Post C
Proposal D

all rely on

One outdated case study
```

That creates fragility.

A relationship map makes that dependency visible.

## Different relationship types should be explicit

### Supports

One asset provides evidence or reasoning for another.

### References

One asset cites or points to another.

### Extends

One asset develops an earlier idea further.

### Distributes

One asset carries another into a wider context.

### Reuses

One asset repurposes the evidence or idea from another.

### Replaces

One asset becomes the stronger or more current version of another.

### Depends on

One asset requires another asset's evidence or definition to remain valid.

Those are operationally different relationships.

## Framework support becomes easier to understand

For example:

```text
AI Buyer Discovery Framework v1.1

Supported by:
Lab #014 — Evidence Weighting
Lab #017 — Buyer-Aligned Proof
Lab #020 — Evidence Coverage
Lab #021 — Buyer-Stage Diagnosis
Lab #022 — Recommendation Strength
Lab #023 — Recommendation Reasons
Lab #024 — Competitor Winning Reasons
Lab #025 — Buyer-Question-to-Action Trace
```

A relationship map makes the framework's evidence base visible.

## Buyer-question mapping becomes more powerful

A single buyer question may connect to several assets.

```text
Buyer Question:
Has this company solved this type of problem before?

Supported by:
Case Study A
Service Page B
Lab Note #017
Customer Testimonial C
Partner Reference D
```

Now the system can see whether the question has strong evidence, weak evidence, duplicated evidence or missing third-party support.

## The map can expose missing links

Sometimes the evidence exists, but the connection is missing.

```text
Strong case study exists
BUT
service page does not reference it
AND
comparison content does not surface it
AND
LinkedIn distribution never used it
```

That is not a proof gap.

It is a relationship gap.

The action is different.

## Relationship gaps can be high leverage

A useful question becomes:

> Which existing asset becomes more valuable if we connect it to the right supporting asset?

This can create leverage without producing anything new.

Same underlying evidence.

Better strategic connections.

## The map helps with consolidation and retirement

If two assets support the same buyer questions, use the same evidence and perform the same job, they may be candidates for consolidation.

Before retiring an old asset, the system can also ask:

> What depends on this asset?

That allows references, redirects and replacement assets to be handled deliberately.

## Relationship mapping improves automation

Once relationships are structured, automation can identify:

- strong proof assets with weak distribution;
- framework pages missing newer supporting research;
- service pages without buyer-aligned proof;
- retired assets still referenced elsewhere;
- high-value Lab Notes that should be reused;
- buyer questions with only one weak supporting source.

That is more useful than automating publishing alone.

## A simple relationship-map structure

A first version could use:

```text
Source Asset
Relationship Type
Target Asset
Buyer Question
Buyer Stage
Evidence Role
Strength
Status
Notes
```

This can still live in a spreadsheet.

The important part is that the relationships are explicit.

## Registry, lifecycle and relationship map serve different jobs

```text
Asset Registry
= what the asset is

Asset Lifecycle
= what happens to the asset over time

Asset Relationship Map
= how the asset connects to the rest of the system
```

Together, they create much stronger system memory.

## The commercial implication

Clients do not only need a library of content.

They need an authority system where proof supports claims, frameworks connect to evidence, service pages connect to proof, distribution connects to source assets and buyer questions connect to the right evidence.

That is where content begins to behave like infrastructure.

## The working principle

My current working principle is:

> Authority does not compound only because more assets exist. It compounds when the right assets are connected in ways that reinforce buyer questions, evidence and entity understanding.

That is why authority systems need an asset relationship map, not just an asset registry.
